# Demo Asset Automation

Regenerate every marketing screenshot and the product demo video from the **live
MultiShop app**, in one command:

```bash
npm run demo:update
```

Run it whenever you change the product UI. Assets are captured from the real app
driving a real API against a real database — never mockups — so what marketing
ships always matches what shipped.

---

## What it does

| Step | Action |
|------|--------|
| 1 | Wipes and reseeds an **isolated demo database** with a realistic fake company: logo, shops, products, customers, sales, inventory, expenses, staff and roles |
| 2 | Boots the API and the SPA on **dedicated demo ports** (never touches your dev server) |
| 3 | Logs in via the API using credentials from `.env.demo` and captures **13 module screenshots** |
| 4 | Records a **60–120s H.264 MP4** product tour of the live app |
| 5 | Publishes to `MARKETING_WEBSITE_PATH` (`public/images/product/`, `public/videos/multishop-demo.mp4`) |
| 6 | Validates every asset and fails the run if anything is missing, blank, mis-sized or out of duration range |

Modules captured: Dashboard, Inventory, Billing, Orders, Customers, Expenses,
Reports, AI Insights, Campaigns, Automations, Roles, Staff, Settings.

## One-time setup

**1. Create your config**

```bash
cp .env.demo.example .env.demo
```

**2. Fill it in**

| Key | Notes |
|-----|-------|
| `DEMO_EMAIL` / `DEMO_PASSWORD` | Login for the demo owner. Throwaway values — but they live in `.env.demo`, never in code |
| `DEMO_DATABASE_URI` | **Must be a separate database whose name contains `demo`.** The seeder wipes it on every run |
| `DEMO_COMPANY_NAME` | Fake company shown in all assets (default `Nova Retail Group`) |
| `MARKETING_WEBSITE_PATH` | Absolute path to the marketing site repo. Leave blank to stop after capture |
| `DEMO_API_PORT` / `DEMO_WEB_PORT` | Defaults `5055` / `4055`. Deliberately not the dev ports |
| `DEMO_VIEWPORT_WIDTH` / `_HEIGHT` | Defaults `1600×900` (16:9) |

`.env.demo` is gitignored.

**3. Make sure dependencies are installed**

```bash
cd client && npm install     # provides Cypress (capture + H.264 encoding)
cd ../server && npm install
```

No new dependencies were added — capture uses the Cypress already in the project,
and its bundled ffmpeg produces the H.264 MP4.

## Usage

```bash
npm run demo:update        # the whole pipeline
```

Individual steps, useful while iterating:

```bash
npm run demo:seed          # reset + reseed the demo database only
npm run demo:publish       # re-copy existing assets to the marketing site
npm run demo:validate      # re-check assets without recapturing
```

Output lands in `scripts/demo/output/`:

```
output/
├── images/          dashboard.png, inventory.png, billing.png, …
├── video/           multishop-demo.mp4
├── api.log          demo API server log
└── web.log          Vite dev server log
```

That folder is gitignored and safe to delete.

## Safety guarantees

These are enforced, not conventions:

- **No production data.** Demo mode resolves `DEMO_DATABASE_URI` and the server
  *refuses to start* if it is unset, identical to `MONGODB_URI`, or if its
  database name doesn't contain `demo` (`server/src/config/db.js`). The
  orchestrator re-checks before seeding.
- **No credential exposure.** Login happens over the API with `{ log: false }`,
  so the login form is never rendered and the password is never typed on camera —
  which matters because this run records video. Validation greps the run logs for
  the password and database URI and fails if either appears.
- **No real PII.** All names, phones, emails and sales are generated by the
  project seeder. The demo owner is `Demo Owner`.
- **Documented seed logins are disabled.** After seeding, every account except
  the demo owner gets a random password, so `owner123` / `staff123` can't be used
  against the demo instance.
- **No port collisions.** The run aborts if the demo ports are already in use, so
  it can never capture your development database by accident.

## Selector policy

Screenshots and the video use **route navigation plus `data-testid` or visible
text** — never pixel coordinates. Restyling a screen changes the captured image;
it doesn't break the run. If a module is renamed:

1. update its entry in `client/cypress/demo/01-screenshots.cy.js`
2. update the `EXPECTED` list in `scripts/demo/validate.mjs`

Validation flags unexpected extra files, so a rename can't silently leave a stale
asset on the marketing site.

---

## Tuning the video length

Validation enforces 60–120s. To adjust, change `PACE` at the top of
`client/cypress/demo/02-tour.cy.js` — it scales every dwell time at once:

```js
const PACE = 1;      // 1.2 = ~20% longer, 0.8 = ~20% shorter
```

## Troubleshooting

| Symptom | Cause / fix |
|---------|-------------|
| `Missing .env.demo` | `cp .env.demo.example .env.demo` and fill it in |
| `database name "…" does not contain "demo"` | Guard working as intended — point `DEMO_DATABASE_URI` at e.g. `multi-shop-demo` |
| `Port 5055 is already in use` | A previous run didn't shut down, or change `DEMO_API_PORT` |
| `video is Ns, outside the 60–120s target` | Tune `PACE` (above) |
| `X.png is only NKB — likely blank or a spinner` | The module didn't finish loading; raise the wait in `cy.gotoModule` or check `output/api.log` |
| Cypress fails to start / `bad option: --smoke-test` | An `ELECTRON_RUN_AS_NODE=1` env var (some IDE terminals set it). The orchestrator already clears it; if you run Cypress by hand, prefix with `env -u ELECTRON_RUN_AS_NODE` |
| `MARKETING_WEBSITE_PATH does not exist` | Fix the path, or clear it to stop after capture |
